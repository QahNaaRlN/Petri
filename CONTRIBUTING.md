# Участие в разработке

Petri находится на экспериментальной стадии. Перед изменением границ безопасности прочитайте [ТЗ](docs/requirements.md), [ТС](docs/technical-specification.md), [инженерные решения](docs/decisions.md) и [текущий статус](docs/status.md).

## Ветки и PR

Поток изменений: **рабочая ветка → `dev` → `main`**. `dev` — интеграционная ветка, `main` — стабильная и целевая default branch. Используйте короткие `feat/<тема>`, `fix/<тема>`, `docs/<тема>` или `chore/<тема>` от `dev` и PR обратно в `dev`; PR из внешних forks также направляются в `dev`. Promotion в `main` допускается только PR из `dev` этого же репозитория. Обновление схемы с добавлением `dev` выполнено по явному указанию владельца.

`main` — default branch; `dev` — общая интеграционная линия. Обе постоянные ветки защищены, используется merge-commit-only режим; squash/rebase/auto-merge отключены. Код Linux, экспериментальный Windows backend и подготовка macOS входят в общую линию. Содержание и ограничения платформ описаны в [статусе](docs/status.md).

Владелец разрешил интеграцию всех кандидатов сначала в `dev`, затем promotion в `main`. Linux принят через [PR #2](https://github.com/QahNaaRlN/Petri/pull/2); Windows/macOS и согласование общей документации представлены в [PR #3](https://github.com/QahNaaRlN/Petri/pull/3). Предыдущий PR #1 сохранён как история rename. Исходные кандидатные SHA и проверки сохранности перечислены в [записи интеграции](docs/branch-integration.md).

Новые рабочие ветки создавайте от актуальной `dev`. Кандидатные ветки — исходные снимки разработки, а не отдельные постоянные ветки выпуска. Слияние кода не заменяет нативную квалификацию Windows/macOS и не объявляет Petri готовым 1.0. Promotion в `main` проходит отдельным PR `dev` → `main` после required checks.

Описывайте конкретную проблему, итоговое поведение, выполненные проверки и оставшиеся ограничения. Не коммитьте секреты, журналы реальных агентов, пользовательские stack images и build outputs. Изменение архитектуры фиксируется в ADR и актуальных ТЗ/ТС. Неподдержанная функция должна возвращать явную ошибку, а не имитировать выполнение.

## Проверки

Используйте toolchain из `rust-toolchain.toml`:

```sh
cargo fmt --all -- --check
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo test --locked --all-features
cargo build --locked --release
python -m unittest discover -s tests -p "test_*.py" -v
```

Для изменений изоляции обязателен настоящий Linux E2E на пригодном хосте; skipped test не является успехом. Команды и требования приведены в [testing.md](docs/testing.md). Не ослабляйте sandbox, не запускайте workload на хосте и не меняйте настройки личного компьютера автоматически ради прохождения теста.

По целевой политике обе постоянные ветки принимают только PR с пятью успешными CI jobs, актуальным base и разрешёнными conversations. Проверка source/base потока включена в portable jobs. Разрешён **только merge commit**; squash и rebase merge отключены, требование линейной истории выключено. Так сохраняется общий граф двух долгоживущих веток без переписывания истории. Для синхронизации явно разрешён отдельный PR `main` → `dev` из того же репозитория.

Force push и удаление `main`/`dev` запрещены, администраторы также соблюдают правила. Прежняя squash-only рекомендация для одной основной ветки заменена этой политикой после явного запроса владельца добавить `dev`.

Эти настройки защиты и merge подтверждены и действуют. Для одиночного maintainer обязательное внешнее approval не требуется; это не разрешение обходить проверки. Настройка репозитория не сливает draft PR автоматически.

Сообщения об уязвимостях отправляйте по [SECURITY.md](SECURITY.md), без публичной публикации credentials или готовой инструкции атаки на пользователя.
