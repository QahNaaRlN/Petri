# ТЗ — Technical Requirements — Petri v0.3

Дата редакции: 2026-10-25 UTC. Статус: инженерная редакция для реализации; не заявление о готовности 1.0. Сохраняет цели ТЗ v0.1/v0.2, устраняет противоречия и отделяет требования от фактической готовности. [Исходники](sources/README.md), [обоснования изменений](decisions.md), [статус реализации](status.md).

## 1. Продукт и задача

Petri — CLI для запуска кодирующих агентов и обычных команд в одноразовых лабораториях. Лаборатория объединяет отдельную рабочую копию исходников, ограниченное окружение исполнения, историю задачи и файловые снимки. Пользователь сохраняет контроль над исходным репозиторием и явно принимает изменения.

Цели продукта: агент не получает прямой доступ к хостовой файловой системе и исходным Git-метаданным; отсутствие внешней сети является безопасным значением по умолчанию; установки системного Git и Docker для базового запуска не требуется; результаты и отказы можно исследовать после выполнения. Совпадение UX на Linux/macOS/Windows остаётся целью полного продукта, а не текущей гарантией.

Не-цели: production orchestration, замена IDE, защита от компрометированного ядра/администратора, автоматическое обнаружение всех секретов в произвольных исходниках, прозрачная совместимость с любым Docker Compose, воспроизведение недетерминированного поведения модели без сохранения всех входов.

## 2. Пользователи и сценарии

| История | Результат |
| --- | --- |
| Как разработчик, я хочу выполнить задачу агента отдельно, чтобы его ошибки не изменяли мой рабочий каталог. | Команда исполняется в lab workspace; исходный HEAD и рабочее дерево не изменяются. |
| Как разработчик, я хочу увидеть diff и принять результат, чтобы контролировать изменения. | Diff доступен до принятия; применение требует явного действия на хосте и безопасной проверки базы. |
| Как исследователь, я хочу журнал запуска, чтобы понять причину ошибки. | Сохраняются task/base/stack, переходы состояния, код выхода и захваченный вывод. |
| Как пользователь офлайн-среды, я хочу импортировать готовый стек, чтобы запускать задачи без registry. | Импорт проверенного локального rootfs/OCI и последующий запуск не требуют сети. |
| Как администратор, я хочу знать реальные ограничения backend, чтобы не полагаться на несуществующую защиту. | Диагностика, явные ошибки и матрица возможностей не скрывают отсутствующие функции. |
| Как пользователь секретов, я хочу разрешать отдельную операцию, чтобы агент не получал долгоживущий credential. | Целевой Vault выполняет узко разрешённую операцию на хосте; до реализации команда отклоняется. |

## 3. Термины и модель доверия

**Lab** — запись задачи, workspace, host-only Git-метаданные, журналы и снимки. **Stack** — импортированный rootfs с идентификатором содержимого. **Checkpoint** — файловый снимок остановленной лабы; не образ памяти процесса. **Blackbox** — журналы доверенного supervisor. **Host operation** — явная команда пользователя вне лабы, например commit/merge.

Недоверенные данные: исходники проекта, конфигурация проекта, задача, команды агента, содержимое импортируемого архива. Доверенные компоненты: Petri, выбранный администратором стек, ядро и хост. Локальная папка импорта считается явно выбранным пользователем источником программ; проверка её хеша не подтверждает подпись издателя.

Сбой установки обязательной защиты запрещает запуск команды. Нет автоматического запуска на хосте, повышения прав, включения сети или fallback к Docker. Решения ADR-001, ADR-007 и ADR-022 обязательны.

## 4. Жизненный цикл

1. Пользователь выбирает локальный Git-репозиторий, задачу, стек и команду/адаптер агента.
2. Petri проверяет конфигурацию и backend до выполнения недоверенной команды.
3. Создаётся независимый workspace из известного коммита с отдельными хостовыми Git-метаданными. Неотслеживаемые и незакоммиченные файлы исходного проекта не переносятся молча.
4. При запуске устанавливаются namespace/mount/seccomp и доступные заявленные лимиты. Lab получает `Running` только для реально запущенной нагрузки.
5. По завершении сохраняются результат, код выхода и доступный вывод; неуспешный setup фиксируется как ошибка, а не как успешная лаба.
6. Пользователь исследует diff, создаёт снимок, восстанавливает остановленную лабу, коммитит результат либо удаляет её.
7. Применение к исходному репозиторию выполняется только отдельной хостовой командой с явным подтверждением. Изменённая база и грязный исходный workspace должны приводить к отказу без потери данных.

Идентификаторы лабы/снимка не являются путями и валидируются до файловых операций. Нельзя удалять произвольный каталог по имени лабы. Изменения состояния и опасные для данных операции должны иметь взаимное исключение. Параллельное удаление работающей лабы запрещено.

## 5. Изоляция и ограничения

Linux backend создаёт отдельные user, mount, PID, network, IPC и UTS namespaces. Корень исполнения не содержит хостовые каталоги; rootfs инструментов доступен только для чтения. Writable workspace и временные каталоги определяются заранее. Mount target, симлинк и путь из конфигурации не могут перенаправить запись наружу. Хостовые Git-метаданные и управляющий blackbox недоступны внутри лабы.

Сеть по умолчанию — `none`: нет интерфейса, ведущего во внешнюю сеть. Запрошенный allowlist до появления полноценного enforcing backend отклоняется. Запрет опасных syscalls задаётся seccomp, `no_new_privs` обязателен. Агент не получает host capabilities.

Rlimits отражаются в документации как ограничения процессов, не как cgroup v2. Целевой групповой лимит CPU/RAM/PID требует отдельной реализации cgroup delegation. Пока он отсутствует, продукт не обещает устойчивость хоста к любому resource exhaustion. Linux backend требует Landlock ABI >=3 (Linux >=6.2 с включённым LSM): отдельные разрешения чтения/исполнения rootfs и записи workspace/tmp/dev, с отказом запуска при невозможности установить правила.

## 6. Git

Продукт использует встроенную Git-библиотеку, системный `git` не является runtime-зависимостью. В текущем инженерном решении это libgit2 через Rust `git2` (ADR-003). Workspace не разделяет writable refs с исходным репозиторием.

Операции host CLI: создание workspace, diff, commit и безопасное принятие результата. Commit содержит доступные provenance-данные без выдуманной модели или подписи. `.env`, `.ssh` и аналогичные запрещённые пути не экспортируются по умолчанию; отказ от экспорта должен быть объяснимым. Submodule и иные неподдерживаемые Git-объекты отклоняются явно. Безопасность не зависит от того, что агент уважает shim в PATH.

Push, произвольный Git RPC и создание PR требуют будущего типизированного брокера с авторизацией ref/remote. Значения main/master запрещены для агентского push по умолчанию; до реализации push не выполняется вообще. Host merge требует явного подтверждения и не подменяет проверку конфликтов. Не исполняются repository hooks и внешние filters/helpers.

## 7. Стеки

Обязательный доступный офлайн-путь: импорт локального rootfs и поддержанного OCI Image Layout, список, разрешение имени в immutable digest, удаление ссылки на стек. SHA-256 OCI descriptors и их размеры проверяются до доверия содержимому. Архивы не могут писать наружу, создавать устройства либо внедрять внешние ссылки; применяются пределы объёма и количества данных.

Одинаковое содержимое хранится по контентному адресу и переиспользуется несколькими лабораториями. Writable workspace не является hardlink к общему стеку. Импорт создаёт необходимые безопасные каталоги mount targets. Registry pull, reproducible stack builder, Dockerfile conversion, SBOM и подписи издателя — отдельные возможности; до реализации возвращается явный отказ.

## 8. Чекпоинты и наблюдаемость

Файловый checkpoint доступен для остановленной лабы, содержит согласованную копию workspace и связанного состояния Git. Restore не восстанавливает процесс, TCP-сессии, секреты или память. Удаление оригинала после снимка не должно менять снимок. Метаданные и пользовательские данные записываются атомарно там, где возможен обрыв операции.

Blackbox на хосте фиксирует создание, запуск, завершение/ошибку, снимки и управляющие действия; данные JSONL разбираются стандартными инструментами. Захваченные stdout/stderr и их тайминги не объявляются точным интерактивным PTY replay без соответствующего backend. Полный fanotify/eBPF аудит каждого exec/file/network события, траектория провайдера и стоимость токенов требуют собственных адаптеров. Отсутствующая стоимость показывается как неизвестная, а не нулевая.

Внутри лабы недопустим доступ на запись к управляющему blackbox. Не включать секреты и полное окружение в `meta.json`; конфигурация и пути показываются только в необходимом объёме. Автоматической публикации IPFS нет.

## 9. Политики и секреты

Конфигурация имеет документированную строгую схему; неизвестные или неподдерживаемые поля приводят к ошибке. Проектная политика не может отключить обязательную изоляцию и перенаправить хостовые записи.

Целевой Vault разделяет Class A signing и Class B bearer. Class A: приватный ключ остаётся на хосте, разрешается конкретная операция. Class B: получатель может прочитать/скопировать выданный токен; этот риск документируется, предпочтителен broker-mediated push. Истечение доступа к раскрытому токену обеспечивается провайдером. Memfd, tmpfs, закрытие fd и scrub не являются отзывом.

До интеграции с OS Keychain, 1Password и аутентифицированным broker команды секретов не должны сохранять реальные credentials в локальном plaintext-файле или имитировать approve. Биометрия и аппаратные ключи проверяются на реальных ОС отдельно. Маскирование логов — дополнительный механизм, не гарантия zero-exposure.

## 10. Docker, IDE и платформы

Docker API публикует только реализованные методы; остальные возвращают 501 JSON. Нельзя заявлять Compose по наличию `/containers/json`. Удаление использует `DELETE /containers/{id}`. Unix endpoint задаётся полным URI `unix:///absolute/path/docker.sock`. Нет автоматического перехвата установленного `docker` и скрытого fallback на иной runtime.

Целевые функции полного продукта: импорт Docker образов/volumes, совместимый запуск контейнеров, networks/volumes/exec/build, devcontainer adapter, опциональный IDE link. Каждая требует собственного acceptance-теста и отмечается отдельно.

Linux — первый runtime backend. На macOS/Windows разрешены переносимые команды управления данными, если они реализованы; запуск без готовой VM/WSL backend возвращает Unsupported. Cross-platform compilation не доказывает изоляцию. VM-образы и стеки считаются отдельно от бинарника.

## 11. Приёмка по фазам

| Группа | Проверяемый результат | Требуемая среда |
| --- | --- | --- |
| AC-1 Lifecycle | Создание и запуск реальной лабы; достоверные состояния; удаление только собственной лабы. Отказ setup не оставляет ложное Running. | Linux с разрешёнными userns/mount/seccomp |
| AC-2 Git | Исходный HEAD не изменён; diff и commit лабы работают; unsafe merge отклоняется; агент не имеет refs исходника. Agent push отклонён до реализации. | Локальные Git-репозитории, без системного Git для продукта |
| AC-3 Isolation | Хостовые файлы недоступны, rootfs read-only, сеть отсутствует, namespace escape не удаётся на проверенной конфигурации. | Реальный isolation runner; destructive fixtures только внутри корректно созданной лабы |
| AC-4 Vault | Signing key не передаётся, операции авторизованы, bearer TTL обеспечен провайдером, реальные TouchID/Hello подтверждены. | Будущая фаза Vault, реальные keychain/provider/ОС |
| AC-5 Stacks | Digest/size верифицируются, вредоносный архив отклоняется, одинаковый стек переиспользуется, офлайн-запуск содержит заявленные инструменты. | Локальные OCI/rootfs fixtures и реальный runtime для запуска |
| AC-6 Observability | Полный обещанный набор событий, точность режима capture, diff и снимков; ограничения явно видны. | Unit/integration + реальные команды |
| AC-7 Docker | Все заявленные методы соответствуют протоколу; 501 для неподдержанных; Compose только после его E2E. | Клиент Docker/Compose и совместимый runtime |
| AC-8 Platforms | AC-1…AC-4 на Linux/macOS/Windows с соответствующим backend. | Реальные пригодные runners и устройства биометрии |

Первый срез охватывает реализуемые части AC-1/2/3/5/6 и честные отказы прочих возможностей. AC-4 нельзя требовать от Phase 1, не реализовав Vault. Финальная приёмка требует весь исходный продукт; частичная матрица не меняет это требование задним числом.

## 12. Качество и готовность релиза

Для кода: `cargo fmt --check`, строгий clippy, unit/integration tests, отдельно opt-in runtime tests; реальные результаты сохраняются в отчёте. Покрытие >80% остаётся целевым гейтом до измерения, не предполагается по числу тестов. Security audit зависимостей учитывает фактическую базу advisories и transitive C-зависимости.

Цели 1.0: один исполняемый файл без системного Git/Docker; измеренный размер <250 МБ, старт тёплой лабы <2 с Linux/<4 с macOS/Windows, p95 <4 с в определённой методике, FS overhead <10%; все AC на трёх ОС; подписанные пакеты/стеки, SBOM, независимый security review, три недели dogfooding на JS/Python/Rust проектах без обнаруженных утечек. Отсутствие обнаруженных утечек не доказывает невозможность утечек.

Холодный старт с загрузкой/распаковкой стека измеряется отдельно. Бенчмарк не выполняется фиктивной командой, которая только создаёт метаданные. Внешние credentials и разрешения для публикации не вшиваются в репозиторий.
