# Ветки и правила репозитория

Редакция: 2026-10-27. Репозиторий: [QahNaaRlN/Petri](https://github.com/QahNaaRlN/Petri).

## Целевая конфигурация

| Объект | Правило |
| --- | --- |
| `main` | Стабильная ветка и целевая default branch вместо `master`; принимает promotion PR только из `dev` этого же репозитория. |
| `dev` | Постоянная интеграционная ветка. Принимает PR рабочих веток и внешних forks; готовый результат поступает отдельным PR в `main`. |
| `feat/*`, `fix/*`, `docs/*`, `chore/*` | Короткоживущие рабочие ветки от `dev`. Целевая база их PR — `dev`. |
| `develop` | Не создаётся: интеграционная ветка называется `dev`. |
| `release/*` | Создаётся только при реальной необходимости сопровождать релиз; сейчас создавать пустую ветку не требуется. Перед использованием включается аналогичная защита. |
| Merge | Разрешён только merge commit (`allow_merge_commit: true`); squash и rebase merge отключены. Рабочая ветка может удаляться после слияния; `main` и `dev` сохраняются. |
| Auto-merge | Возможность автоматического слияния выключена (`allow_auto_merge: false`); существующие draft PR не сливаются при настройке репозитория. |

Поток изменений: **рабочая ветка → `dev` → `main`**. Для обеих постоянных веток обязательны PR, успешные пять проверок ниже, актуальность ветки относительно базы и разрешение всех review conversations. Требование линейной истории выключено (`required_linear_history: false`), поскольку используется merge commit. Force push и удаление `main`/`dev` запрещены; правила применяются также к администраторам. Прямой push не является штатным способом внести изменения.

В `main` допускается promotion PR только с head `dev` из `QahNaaRlN/Petri`; одноимённая ветка `dev` чужого fork не подходит. Feature/fix/docs/chore и fork PR направляются в `dev`. Отдельный PR `main` → `dev` из того же репозитория явно разрешён для обратной синхронизации. Проверка потока включена в существующие portable CI jobs, поэтому список пяти required checks сохраняется: сами GitHub branch protection rules не выражают ограничение «только этот source branch».

Ранее предлагавшаяся схема без `dev` заменена этим двухветочным процессом по прямому указанию владельца. Из-за двух долгоживущих веток прежний squash-only подход также заменён merge-commit-only: сохраняется граф происхождения изменений, promotion и обратная синхронизация не требуют переписывать историю и не сталкиваются с требованием линейности. Строгие проверки актуальности PR остаются включёнными. Переход не означает автоматическое слияние существующих draft PR.

Проект пока ведётся одним владельцем: обязательное независимое approval не устанавливается, чтобы не блокировать работу единственного maintainer. Это не отменяет PR, CI и проверку изменений самим владельцем. При появлении команды число обязательных approvals пересматривается отдельно.

| Обязательная проверка CI | Что проверяет |
| --- | --- |
| `Build and portable tests (ubuntu-24.04)` | Linux host-side tests, fmt/clippy и release build |
| `Build and portable tests (macos-14)` | Переносимые host-side tests и build; не квалификация native macOS isolation |
| `Build and portable tests (windows-2022)` | Переносимые host-side tests и build; не квалификация native Windows isolation |
| `Native Linux isolation (required; no skipped success)` | Настоящий Linux namespace/rootfs/network E2E |
| `Dependency vulnerability audit` | Проверка зависимостей по RustSec |

При переименовании CI job сначала согласуется соответствующее required check: устаревшее имя может навсегда заблокировать merge. Изменения CI и правил защиты проходят проверку, не обходятся фиктивными успешными статусами.

## Применение GitHub settings с локальной авторизацией

Для воспроизводимой проверки и восстановления настроек подготовлен [scripts/configure_github.py](../scripts/configure_github.py); текущая настройка уже завершена через GitHub UI. По умолчанию скрипт показывает план без изменения репозитория (`--dry-run` — явный эквивалент); применение требует `--apply` и административных прав локального GitHub CLI. При использовании скрипта нужны Python 3.10+, Git и `gh`, авторизованный владельцем:

```sh
gh auth login
python scripts/configure_github.py --dry-run --delete-master
python scripts/configure_github.py --apply --delete-master
python scripts/configure_github.py --verify --delete-master
```

Предпочтителен fine-grained PAT с доступом **только к `QahNaaRlN/Petri`** и разрешениями **Administration: Read and write**, **Contents: Read and write**, **Pull requests: Read and write**: они нужны для настроек, проверки/создания refs, безопасного удаления `master` и переноса открытых PR. Альтернатива для classic PAT — scope `repo`. Это разрешения токена локального CLI, а не просьба передать токен ассистенту. Не вставляйте токен в чат, командную строку с сохраняемой историей, исходники или коммит; используйте интерактивный `gh auth login` и штатное защищённое хранилище GitHub CLI. Сам скрипт не выполняет login и не читает значения токенов.

Перед применением просмотрите dry-run. `--verify` только читает настройки и возвращает ошибку при несовпадении; `--report PATH` сохраняет очищенный JSON-отчёт. Скрипт ограничен указанным репозиторием на github.com, не переписывает историю и не сливает PR. `--apply` переводит default на `main` и настраивает обе ветки; дополнительный `--delete-master` разрешает удалить старую ветку только после проверки, что все её коммиты сохранены в истории `main`, открытых PR с legacy base/head нет и она больше не default. Без флага удаление не выполняется. `--verify --delete-master` дополнительно проверяет отсутствие `master`.

После применения перечитываются default branch, merge policy и защита обеих веток. Если GitHub возвращает 401/403, процесс останавливается с объяснением прав; частично выполненное применение не считается успехом и требует проверки снимка. Не отключайте CI и не заменяйте результат текстовым отчётом об успехе.

## Локальная копия Windows

Желаемый путь: `D:\PersonalProjects\Petri`. Фактическое клонирование на личный диск Windows не выполнялось; работа продолжена в облачной среде по согласованию с владельцем. Подготовлен безопасный [scripts/clone-windows.ps1](../scripts/clone-windows.ps1): по умолчанию выбирает этот путь и ветку реализации, проверяет существующий каталог, origin и чистоту рабочего дерева. До слияния PR #1 ручные команды для нового каталога в PowerShell:

```powershell
New-Item -ItemType Directory -Force 'D:\PersonalProjects' | Out-Null
git clone --branch feat/linux-native-candidate https://github.com/QahNaaRlN/Petri.git 'D:\PersonalProjects\Petri'
git -C 'D:\PersonalProjects\Petri' status
```

Если каталог уже существует, не удаляйте и не сбрасывайте его: сначала проверьте `git status`, origin и текущую ветку. Стандартный `git clone` на Windows требует установленного Git; это инструмент разработки репозитория, а не runtime-зависимость самого Petri.

Скрипт Windows не рассчитан на одновременное редактирование каталога другим процессом. Он перепроверяет origin, ветку и чистоту после fetch и перед ff-only merge, однако не может транзакционно заблокировать произвольные внешние операции Git.

## Проверки подготовленных инструментов

Текущие проверки: **55 Python-тестов прошли** (48 настройки и 7 маршрутизации веток). Покрыты запреты обхода и ослабления правил, обе постоянные ветки, ошибочные ответы, 403, ancestry и устаревший SHA при удалении. Реальный локальный Git-тест подтверждает: устаревшая lease отклоняет удаление, актуальная удаляет только ожидаемый ref.

До применения настроек через UI read-only GitHub dry-run с `--delete-master` завершился со статусом `planned`, выполненных записей — 0; [сохранённый план](verification/repository-settings-dry-run.json) отражает обе ветки и условное удаление. Тогда попытка применения скриптом остановилась на первом `PATCH` с HTTP 403, успешных административных записей скрипта — 0. Это исторический результат ограниченной integration, а не текущая блокировка: позднее настройки завершены через авторизованный GitHub UI и подтверждены, `master` удалена отдельной атомарной Git-операцией. Скрипт совместим с GitHub CLI 2.46 без `--slurp`.

Удаление использует Git protocol с `--force-with-lease=refs/heads/master:<проверенный SHA>`, а не REST DELETE: сервер атомарно отказывает, если ref изменился. Это условное удаление уже проверенной ветки, а не переписывание истории. Для операции нужен установленный Git и существующая авторизация `gh`; credential helper постоянный, токен не читается скриптом и не передаётся в аргументах. Изменённый URL push, чужой git-dir или неоднозначная конфигурация приводят к отказу. Весь набор GitHub settings не является транзакцией, поэтому не проводите параллельные административные изменения.

CI проверяет эти тесты на трёх ОС; Windows job дополнительно разбирает PowerShell через штатный parser и проверяет `-WhatIf` без создания каталога. В этой облачной Linux-среде PowerShell отсутствует; результат Windows-проверки публикуется в PR.

Dependabot направляет обычные обновления в `dev`; CI допускает `dependabot/*` только от настоящего `dependabot[bot]` из этого репозитория. Security PR, автоматически открытый GitHub в default `main`, необходимо явно перенаправить в `dev`, затем продвинуть обычным promotion PR; исключения обхода main не добавлены.

После успешной Git lease-операции REST API может кратковременно возвращать старую ссылку. Инструмент выполняет ограниченные повторные GET-проверки без повторной записи; если подтверждение не пришло, сохраняет `pending_verification` и факт успешной lease-операции. При этой миграции окончательное отсутствие `master` подтверждено и API, и `git ls-remote`; данные обеих постоянных веток не изменились.
