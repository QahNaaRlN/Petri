# Реестр замечаний и инженерных решений

Версия 0.3, 2026-10-25. Владелец разрешил приоритет инженерного решения над исходными ТЗ/ТС при явной фиксации изменения в коде и документах. Этот реестр фиксирует такие изменения; он не является свидетельством завершённой реализации. Актуальный статус каждого компонента приведён в [матрице](status.md).

## ADR-001. Граница безопасности

**Замечание.** Формулировки «хост неуязвим», «полная безопасность» и «без legacy-ошибок» не являются проверяемыми гарантиями. Контейнер использует ядро хоста; уязвимость ядра может нарушить изоляцию.

**Решение.** Угроза — ошибочная или злонамеренная команда внутри лабы при исправном ядре и доверенном Petri. Защищаем недоступные для монтирования хостовые данные и исходный репозиторий, запрещаем сеть по умолчанию. Доверяем администратору, ядру, самому исполняемому файлу Petri и явно импортированному стеку. Успех запуска допустим только после установки обязательных ограничений. Защита от враждебного хостового пользователя с тем же UID, компрометации ядра и аппаратных побочных каналов не заявляется.

## ADR-002. Git worktree не является границей доступа

**Замечание.** Обычный worktree разделяет refs, objects и конфигурацию с исходным репозиторием. Права 0700 не разделяют процессы с одинаковым хостовым UID. Файл `.git` с недоступным `gitdir` сам по себе не создаёт работающий Git внутри контейнера.

**Решение.** Использовать независимую лабораторную копию и отдельные Git-метаданные на хосте, вне корня, доступного процессу лабы. Ни исходный `.git`, ни лабораторные метаданные не монтируются внутрь. Команды diff/commit/merge выполняет доверенный CLI Petri на хосте. Интерактивный Git внутри агента и универсальный Git RPC остаются отдельными задачами. Отступление от shared worktree увеличивает расход диска, но существенно упрощает проверяемую защиту refs.

## ADR-003. Встроенная Git-библиотека

**Замечание.** Выбор gitoxide в исходниках не доказывает наличие всех нужных write/worktree/transport API. Подмена вызовом системного `git` нарушила бы установку одним бинарником.

**Решение.** Для текущей реализации использовать `git2` 0.21 со встроенным libgit2, без сетевых transport features. Системный Git не нужен продукту. Это сознательное отступление от требования «чистый Rust»: основное приложение написано на Rust, зависимость содержит C-код. Встроенная библиотека не должна запускать shell, hooks, credential helpers или произвольные фильтры. Будущую замену на gitoxide оценивать по функциональности, тестам и зависимостям, а не только языку реализации.

## ADR-004. Git-брокер не принимает произвольную командную строку

**Замечание.** `git -c ...`, `core.sshCommand`, hooks, remote helpers, pathspec и конфигурация дают способы выполнения хостовых программ либо доступа к чужим путям. Проверки одного `push main` недостаточно. `reference-transaction` hook не заменяет авторизацию и не обязательно исполняется при прямых библиотечных операциях.

**Решение.** Не реализовывать универсальный passthrough к Git на хосте. Будущий брокер принимает типизированные операции с серверным определением lab ID, repository ID, разрешённых refs и remotes. Нельзя доверять указанному агентом пути, UID или lab ID. В текущем срезе push не поддерживается; merge доступен только явной хостовой команде. Исходный репозиторий с незакоммиченными изменениями нельзя молча перезаписывать.

## ADR-005. Seccomp фильтрует системные вызовы

**Замечание.** Seccomp может учитывать номера и скалярные аргументы вызовов, но не обеспечивает семантическую фильтрацию путей и доменных имён. Фиксированное «80 вызовов» не является самостоятельным критерием безопасности и совместимости.

**Решение.** Seccomp — отдельный слой защиты от опасных вызовов после настройки namespace/mount. Обязательны проверка архитектуры, запрет повышения привилегий и отсутствие возможности отключить профиль агентом. Файловый доступ обеспечивается mount namespace, безопасными mount targets и read-only rootfs; сеть — отдельным network namespace. Список разрешений должен проверяться на реальных рабочих нагрузках; несовместимая нагрузка завершается ошибкой, профиль автоматически не ослабляется.

## ADR-006. Landlock: версии, разрешения, читаемый rootfs

**Замечание.** ABI v2 Landlock появился в Linux 5.19, ABI v3 — в 6.2. Правил DENY у Landlock нет: модель задаёт разрешённый доступ. Выдача чтения всему `/workspace` с последующим «deny .env» не работает как описано. Запрет чтения всего rootfs кроме трёх каталогов блокирует загрузчик, библиотеки и программы.

**Решение.** Linux backend требует Landlock ABI >=3 и проверяет его через syscall; при отсутствии ABI запуск отклоняется. Разрешаются чтение/исполнение rootfs и запись в `/workspace`, `/tmp` и ограниченный `/dev`; deny-правила не имитируются. Основной файловый барьер — отдельный корень с read-only инструментами и writable mount только для разрешённых каталогов. Запрещённые секретные файлы не должны попадать в экспорт исходников. Установка Landlock реализована в коде; реальное применение правил требует runtime E2E на пригодном хосте.

## ADR-007. Rootless, capabilities и системные зависимости

**Замечание.** User namespaces могут быть отключены политикой дистрибутива, AppArmor либо внешним контейнером. OverlayFS, cgroup delegation и eBPF также доступны не в любой rootless-среде. Требование «без root» не означает «без требований к хосту».

**Решение.** Предоставить диагностику реальной доступности backend. При невозможности создать обязательный namespace, mount, seccomp или лимит запуск завершается ошибкой до выполнения полезной нагрузки. Нельзя автоматически запускать её без изоляции, через sudo или напрямую на хосте. Отказ backend считается ожидаемым исходом теста доступности, но не успешным тестом изоляции. Нативный Linux backend не зависит от внешней команды `unshare`.

## ADR-008. Ресурсы: rlimits и cgroup — разные гарантии

**Замечание.** RLIMIT_AS ограничивает виртуальное адресное пространство процесса, RLIMIT_CPU — его процессорное время. Это не лимиты суммарного RSS, CPU bandwidth и количества процессов всей лабы. RLIMIT_NPROC связан с UID и привилегиями; он не заменяет cgroup `pids.max`.

**Решение.** Честно называть применённые лимиты rlimits и описывать их ограничения. Групповые hard limits требуют проверяемой cgroup v2 delegation и включённых контроллеров; до их реализации не обещать защиту хоста от всех вариантов ресурсного истощения. Прерывание и уборка должны охватывать процессы namespace, а не только лидера.

## ADR-009. Сеть: `none` и доменный список разрешений

**Замечание.** `CLONE_NEWNET` создаёт namespace; выражение «нет net ns вообще (CLONE_NEWNET)» противоречиво. DNS-фильтр не запрещает прямой доступ по IP, альтернативные резолверы, DNS rebinding и доступ к другому домену на том же CDN IP. Cgroup BPF обычно требует привилегий; пакеты slirp/pasta могут исходить от хостового посредника, вне cgroup лабы.

**Решение.** Реально поддерживать `network: none`: отдельный namespace без внешнего интерфейса. Любой ненулевой сетевой режим отклонять до запуска, пока нет проверяемого посредника. Будущий разрешающий прокси обязан валидировать адрес назначения, протокол, DNS/IPv6, редиректы и исключать обход через прямые соединения. DNS allowlist и IP allowlist нельзя представлять как точную доменную изоляцию.

## ADR-010. Секреты двух классов и авторизация операций

**Замечание.** SSH/GPG signing позволяет не выдавать ключ, но доступный агенту signing oracle всё равно может выполнять нежелательные операции. Bearer-токен, env или файл в tmpfs доступны процессу, получившему их. Маскирование логов не меняет этого свойства.

**Решение.** Class A: ключ остаётся вне лабы, а брокер проверяет назначение, операцию, repository/ref и область разрешения. Class B: факт раскрытия получателю явно документируется; предпочтителен брокер, сам выполняющий разрешённую операцию без передачи токена. Vault не считается реализованным по наличию конфигурации или интерфейса команды. Недоступная интеграция возвращает Unsupported.

## ADR-011. Memfd и TTL не отзывают секрет

**Замечание.** Memfd уже является анонимным файлом, обычный `unlink` не даёт ему заявленного свойства. После SCM_RIGHTS получатель владеет собственным дескриптором. Закрытие fd у брокера не закрывает его у получателя; затирка памяти не удаляет уже сделанные копии. Многие провайдеры не умеют выпускать одноразовые токены на произвольные две минуты.

**Решение.** Отзыв доступа обеспечивается истечением/отзывом credential на стороне провайдера либо прекращением всех операций посредника. TTL разрешения брокера и срок действия раскрытого токена — разные поля и разные гарантии. До такой реализации не выдавать секреты и не заявлять тест «после TTL токен исчез».

## ADR-012. Аудит и удаление секретов из логов

**Замечание.** Постобработка оставляет окно хранения исходного секрета. Простая замена шаблона не ловит разбитый по чанкам, закодированный или преобразованный токен. Агент может менять свои writable логи; append-only на уровне приложения не является криптографической неизменностью. Просмотр escape-последовательностей недоверенного терминала тоже имеет риск.

**Решение.** Управляющие журналы хранить на хосте, вне workspace, с закрытыми правами; `logs` внутри лабы не выдаёт возможности изменить историю supervisor. Записывать только необходимые поля. Терминальный журнал описывать согласно реальному формату и режиму capture: pipe не является PTY, asciinema-обёртка не доказывает точность интерактивного replay. Vault/redaction и полный syscall/process/network audit требуют отдельных тестов. Трейлеры коммита с provenance — данные, не криптографическая подпись.

## ADR-013. OCI: доверие, целостность и распаковка

**Замечание.** SHA-256 доказывает соответствие байтам descriptor, но не доверие издателю. Tar может содержать `..`, абсолютные имена, ссылки наружу, устройства, whiteout и бомбы распаковки. Hardlink writable workspace к общему стеку нарушает иммутабельность. Docker image-save tar не равен OCI layout.

**Решение.** Поддержать отдельные явные импорты локального rootfs и OCI Image Layout с проверкой digest/size, ограничениями ресурсов и безопасной обработкой слоёв. Не импортировать устройства и ссылки наружу. Контентный адрес дедуплицирует один стек между лабами; персистентное хранилище нельзя менять из лабы. Подпись cosign, SBOM, registry pull, Dockerfile/Nix builder и Docker-save conversion не подменяются проверкой хеша и не считаются реализованными автоматически.

## ADR-014. Политика и пользовательский YAML

**Замечание.** Пример `network: ["*"] except [...]` не является корректной самостоятельной YAML-схемой. Неизвестные поля, опечатки и неподдерживаемые правила могут создавать ложное ощущение защиты. `**/.env` не покрывает все возможные имена секретов. Проектный конфиг также является недоверенным вводом.

**Зависимости.** По результатам RustSec убраны `serde_yaml`/`unsafe-libyaml` (неподдерживаемый парсер) и git2 0.20 (RUSTSEC-2026-0183/0184). Используется `serde-saphyr` 2 с feature `deserialize`, без include, filesystem-resolver и environment properties; git2 обновлён до 0.21. Информационные предупреждения не подавляются.

**Решение.** Документировать одну точную схему и отклонять неизвестные поля/неподдерживаемые требования до запуска. Политика не может включить отключённый backend либо ослабить обязательную изоляцию. Файлы секретов не экспортируются по умолчанию, но Petri не обещает автоматически распознавать любые секреты в произвольном tracked-файле. Не читать системные env/credential файлы ради диагностики.

## ADR-015. Docker API и Compose

**Замечание.** Удаление контейнера — `DELETE /containers/{id}`, а не `POST .../remove`. Кроме одного списка контейнеров требуются version negotiation, inspect, stream logs, attach, wait, images, network/volume API и семантика ошибок. Compose обычно создаёт сеть по умолчанию даже без явного `networks` в YAML. `DOCKER_HOST` для unix-сокета требует форму `unix:///...`, не просто путь с `~`.

**Решение.** Публиковать точную матрицу поддержанных методов. Необработанные методы возвращают 501 JSON; отсутствие контейнера — 404, неверный запрос — 400. Read-only inspection не называется Docker compatibility для запуска workloads. Не заменять `/usr/local/bin/docker` автоматически. Fallback к настоящему Docker — отдельное явное действие пользователя, поскольку оно меняет границу безопасности.

## ADR-016. Без демона и жизненный цикл

**Замечание.** Долгоживущий Vault и Docker socket являются сервисами даже при daemonless core. Фраза «`petri create` завершается вместе с лабой» не определяет, кто отвечает за статус, остановку и PID reuse. Записанный PID не доказывает идентичность процесса после перезапуска.

**Решение.** Разделять foreground run, состояние задачи и опциональные сервисы. Сериализовать переходы состояния, фиксировать неуспешный запуск, не оставлять `Running` после завершения. Для background supervisor нужны идентификация процесса и восстановление после crash. Отдельный сокет не требуется для базовой изоляции; опциональный сервис не запускается без явной команды.

## ADR-017. Каноническое хранилище и чекпоинты

**Замечание.** В v0.1 одновременно указаны глобальный `~/.petri/labs` и проектный `.petri/labs`. Symlink для IDE может давать неожиданный доступ или попадать в Git. Снапшот overlay upperdir не является снапшотом памяти/процессов; копирование работающего дерева без координации может быть несогласованным.

**Решение.** Использовать одно глобальное хранилище с возможностью явного выбора пути. Проектный symlink — необязательная отдельная команда. Чекпоинт текущего среза — файловый снимок workspace и относящегося к нему состояния Git, только при остановленной нагрузке. Restore не восстанавливает процесс/сеть/память. Снимки не используют writable hardlinks и не переходят по symlink наружу.

## ADR-018. Mac/Windows и установка одним бинарником

**Замечание.** macOS VM требует entitlement, подписывания, образа гостя и поддерживаемой среды виртуализации. На Windows WSL2 может отсутствовать/быть отключён, требовать перезагрузки; hosted runner не гарантирует nested virtualization. HCS не запускает произвольный Linux rootfs как Windows-контейнер. Встроенный бинарник не содержит все стеки и VM автоматически.

**Решение.** Не называть компиляцию или mock-тест настоящим E2E на этих ОС. До готовности backend возвращать Unsupported. При реализации явно документировать загрузки, права, системные компоненты и отдельные образы. Размер исполняемого файла измерять отдельно от гостевых образов/стеков и полного установочного пакета.

## ADR-019. Приёмка, метрики и фазирование

**Замечание.** Phase 1 в v0.2 требует AC-1…AC-6, хотя AC-4 включает Vault/биометрию из Phase 3. `cargo test --all-features` не делает privileged-тесты доступными. Наличие GitHub Actions YAML не означает успешный запуск CI. Порог покрытия нельзя заявлять без отчёта.

**Решение.** Отдельно учитывать функциональность, выполненные тесты, проверки на подходящем runner и релизные гейты. Метрики старта задаются с различением холодного/тёплого запуска и включённой/исключённой загрузки стека. Rlimits не выдаются за FS overhead <10%. Биометрия, подписи пакетов, три недели dogfooding и независимый security review остаются открытыми до реального выполнения. Указанные в v0.2 недели — плановая оценка, не доказательство срока.

## ADR-020. Кэш и provenance

**Замечание.** `hash(repo+stack+prompt)` недостаточен: влияют base commit, грязное дерево, конфигурация, модель, инструменты, версия Petri и разрешения. Возврат diff без проверки базы может применить чужое изменение. IPFS делает данные публичными при публикации и не заменяет управление доступом.

**Решение.** Пока не реализован проверяемый ключ и проверка applicability, не включать кэш результатов агента. Provenance локально содержит известные base/stack/task/tool данные, отсутствующие значения не выдумываются. Не публиковать blackbox в IPFS автоматически; перед публикацией нужны явная команда, проверка секретов и политика хранения. Трейлеры provenance и подпись коммита считаются разными возможностями.

## ADR-021. Даты, внешние ссылки и исходники

**Замечание.** ТЗ v0.1 датировано на день позже даты чтения. Утверждения о релизах 1Password в исходниках не подтверждены кодом или независимым исследованием. Публичные artifact-ссылки могут измениться/истечь.

**Решение.** Сохранить полученные DOCX и текст без исправлений, отдельно публиковать новые редакции и журнал решений. Не выдавать описание возможного стороннего API за готовую интеграцию. Писать неизвестные внешние ограничения явно, использовать доступные API только после проверки.

## ADR-022. Отсутствие функции — проверяемый результат

**Замечание.** Stub, успешный mock, созданный каталог или print JSON могут выглядеть как работающий контейнер, Vault или checkpoint.

**Решение.** Команды обязаны возвращать ненулевой код и объяснение для неподдерживаемых режимов. Локальное создание метаданных не переводит lab в `Running`. Unit-тесты подмен не являются подтверждением реальной изоляции. Итоговый отчёт обязан перечислять невыполненные части исходного объёма и внешние блокировки отдельно от дефектов реализации.
